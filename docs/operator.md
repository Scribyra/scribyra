# Kubernetes operator

Decided by Paul on 18 November 2026: organisation deployments are cloud native, and the
**Scribyra operator** is the way to deploy them. A single-node k3s cluster is the small-install
path. This page is the operator's reference; the design is in
[org-sync-design.md, section 10](org-sync-design.md#10-deployment-on-kubernetes), the service it
deploys in [service.md](service.md).

The operator (`crates/operator`, binary `scribyra-operator`, Rust with kube-rs) watches
`Scribyra` resources and runs, for each, one deployment: the `scribyra-sync` API, the static web
app, optional compile workers, PostgreSQL (yours or CloudNativePG) and object storage (yours or a
single-node Garage), with ingress, TLS, network policies and upgrades.

## What it runs

For a resource named `acme` in namespace `acme`:

| Component | Objects | Notes |
| --- | --- | --- |
| Configuration | Secret `acme-config` (`service.json`) | Generated from the spec; checked with the service's own validation before anything is deployed. Each referenced secret is mounted as its own read-only file. |
| API and sync | Deployment, Service, PodDisruptionBudget `acme-api`; HorizontalPodAutoscaler when `autoscaling` is set | `scribyra-sync serve` on 8787; liveness `/health`, readiness `/ready`. |
| Web app | Deployment, Service, PodDisruptionBudget `acme-web` | Static files on 8080, same origin as the API (below). |
| Compile workers | Deployment `acme-worker` (`compile: server` or `both`); KEDA `ScaledObject` optionally | `scribyra-sync compile-worker`, `hostUsers: false`, optional `runtimeClassName`, memory-backed scratch. |
| Migrations | Job `acme-migrate-<version>` | `scribyra-sync migrate`, run to completion before any Deployment uses a new release. |
| Routing | Ingress `acme` (or Gateway API `HTTPRoute`, plus a cert-manager `Certificate`) | `/v1` to the API, everything else to the web app, on `https://<domain>`. |
| Network | NetworkPolicies `acme-default-deny`, `-api`, `-web`, `-migrate`, `-worker`, `-garage`, `-db` | See [Security model](#security-model). |
| PostgreSQL | external Secret, or CloudNativePG `Cluster` `acme-db` (+ `ScheduledBackup`) | The Cluster has no owner reference: deleting it deletes the database volumes. |
| Object storage | external S3, or Garage: StatefulSet, Service, ConfigMap `acme-garage`, Secrets `acme-garage-internal`, `-tls`, `-s3` | Single node, one volume, TLS proxy sidecar. |
| Master key | Secret `acme-master-key` (server-readable mode, unless `masterKeyRef`) | Generated once, never overwritten, never owned. |

**The web app is a separate image** (`scribyra-web`: the built app and `static-web-server`), not
served by the API image. The app and the API still share one origin through path routing, which
is what the design needs (CORS and the OIDC return are same-origin). Reasons: the app's build
(Vite, the WebAssembly module, the BusyTeX compiler assets) is a different pipeline from the
service's and releases on its own cadence with Pages; the API image stays small and free of
frontend files; the web pods need no database, secrets or egress at all, so they get the
strictest policy; and static files can be scaled and cached apart from the API. The cost is one
more Deployment and image per release, which the operator manages anyway. `nix/operator.nix`
builds it (`lib.<system>.webImage <built app>`).

## Install the operator

The operator is installed on its own; deployments are created afterwards as resources.

**One manifest** (namespace `scribyra-system`, the CRD, least-privilege RBAC, the Deployment):

```sh
kubectl apply --server-side -f deploy/operator/operator.yaml
kubectl -n scribyra-system rollout status deployment/scribyra-operator
```

`deploy/operator/operator.yaml` is generated by `scribyra-operator manifests` (a test fails when
it drifts from the code). For another image or registry:

```sh
nix develop .#operator -c cargo run -p scribyra-operator -- manifests \
  --image registry.example/scribyra/scribyra-operator:0.1.0 --registry registry.example/scribyra
```

**Helm** (the operator only; no Scribyra deployments):

```sh
helm install scribyra-operator deploy/helm/scribyra-operator \
  --namespace scribyra-system --create-namespace \
  --set image.repository=registry.example/scribyra/scribyra-operator --set registry=registry.example/scribyra
```

Values: `image.*`, `imagePullSecrets`, `registry` (prefix of the images the operator deploys),
`watchNamespace` (one namespace instead of the cluster), `replicas` (extra replicas stand by on
the leader lease), `resources`, `nodeSelector`, `tolerations`, `affinity`. Helm installs the CRD
from `crds/` on first install only; apply the CRD from `operator.yaml` when upgrading.

**Images.** All are built with Nix from this checkout (no Docker daemon, no mutable base image):

| Image | Build | Tag |
| --- | --- | --- |
| `scribyra-operator` | `nix build .#operator-image` | workspace version |
| `scribyra-sync` (API, migrations) | `nix build .#service-image` | the release (`spec.version`) |
| `scribyra-web` | `lib.<system>.webImage ./dist` | the release |
| `scribyra-worker` | not built yet (slice 15) | `<release>-texlive-<small\|medium\|full>` |
| `scribyra-garage` | `nix build .#garage-image` | Garage 1.x version |

Each system builds natively (`x86_64-linux`, `aarch64-linux`); a multi-arch image is the two
pushed under one manifest list (for example `crane index append` or `skopeo` in CI on an amd64
and an arm64 runner). Pushing, signing (cosign) and SBOMs are slice 21. The operator deploys
`<registry>/<image>:<tag>`; `spec.images` overrides each image.

## Single-node quickstart (k3s)

On one Linux machine with a public DNS name pointing at it (`scribyra.lab.example.org` below)
and ports 80 and 443 open. k3s brings Traefik as the ingress controller and the local-path
storage class.

```sh
# 1. k3s (single node).
curl -sfL https://get.k3s.io | sh -
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml

# 2. cert-manager and an ACME issuer (Traefik answers the HTTP-01 challenge).
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.19.1/cert-manager.yaml
kubectl -n cert-manager rollout status deployment/cert-manager-webhook
kubectl apply -f - <<'EOF'
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: letsencrypt}
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: it-admin@lab.example.org
    privateKeySecretRef: {name: letsencrypt-account}
    solvers: [{http01: {ingress: {ingressClassName: traefik}}}]
EOF
# Without a public name, use a self-signed issuer instead:
#   kubectl apply -f - <<<'{"apiVersion":"cert-manager.io/v1","kind":"ClusterIssuer","metadata":{"name":"letsencrypt"},"spec":{"selfSigned":{}}}'

# 3. CloudNativePG (provisioned PostgreSQL).
kubectl apply --server-side -f https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/release-1.27/releases/cnpg-1.27.1.yaml
kubectl -n cnpg-system rollout status deployment/cnpg-controller-manager

# 4. The operator.
kubectl apply --server-side -f deploy/operator/operator.yaml
kubectl -n scribyra-system rollout status deployment/scribyra-operator

# 5. A deployment: the OIDC client secret, then the resource.
kubectl create namespace lab
kubectl -n lab create secret generic lab-oidc --from-literal=client-secret='<from your IdP>'
kubectl apply -f deploy/operator/samples/quickstart.yaml
kubectl -n lab wait scribyra/lab --for=condition=Ready --timeout=15m
kubectl -n lab get scribyra lab
```

Register `https://scribyra.lab.example.org/v1/sso/callback` at the identity provider (see
[service.md, Single sign-on](service.md#single-sign-on-oidc)). Then **back up the master key**
(`kubectl -n lab get secret lab-master-key -o yaml`) somewhere other than the cluster.

Versions above (cert-manager 1.19.1, CloudNativePG 1.27.1) are the ones these instructions were
written against; use current releases and pin them. Before images are published, load locally
built ones into k3s with `k3s ctr images import`.

## The `Scribyra` resource

`apiVersion: scribyra.com/v1alpha1`, `kind: Scribyra`, short name `scr`, namespaced. The API
server enforces the OpenAPI bounds and CEL rules below; the operator additionally runs the
service's own configuration validation and reports a refusal as `Degraded`/`InvalidSpec`
without deploying anything. Samples: [`deploy/operator/samples/`](../deploy/operator/samples).

| Field | Default | Meaning |
| --- | --- | --- |
| `version` | required | Release (image tag), `X.Y.Z[-pre]`. Changing it upgrades ([Upgrades](#upgrades)). |
| `domain` | required | DNS name; the app, API and OIDC callback are at `https://<domain>`. |
| `displayName` | resource name | Shown in sign-in and project lists (`deployment.name`). |
| `encryption` | `serverReadable` | `serverReadable` or `endToEnd`. **Immutable** (CEL transition rule). |
| `oidc.providers[]` | required, 1–16 | `name` (lowercase ID, unique), `label`, `issuer` (https), `clientId`, `clientSecretRef {name, key}`, `emailDomains`, `roleMapping {groupsClaim, adminGroups, memberGroups}` (groups need `groupsClaim`), `guest {claim, equals}`, `offlineAccess`, `sessionHours`, `recheckMinutes`, `scopes`. |
| `policy` | | `offlineAllowed` (true), `linkSharing` (false), `guests` (`off`/`shared`), `admins` (bootstrap administrators: emails or `issuer#subject`). |
| `compile.mode` | `browser` | `browser`, `server` or `both`; `server`/`both` need `serverReadable` (CEL). |
| `compile.texlive` | `small` | Worker image variant: `small`, `medium`, `full`. |
| `compile.runtimeClassName` | none | For example `gvisor`. |
| `compile.workers` | min 0, max 8, concurrency 2, scaler `operator` | Replicas bounds, jobs per worker, `scaler: operator` or `keda` (+ `prometheusAddress`). |
| `compile.limits` | as the service | `cpuSeconds`, `wallSeconds`, `memoryMiB`, `scratchMiB`, `outputMiB`, `passes`, `queue`, `perMemberPerHour`. |
| `compile.resources` | derived from limits | Worker pod resources. |
| `postgres.external` | | `secretRef {name, key}` with the URL; `cidrs` and `port` (5432) for the egress policy. |
| `postgres.provisioned` | | `storageSize` (20Gi), `instances` (1), `storageClassName`, `imageName`; needs CloudNativePG. |
| `storage.s3` | | `endpoint` (https), `bucket`, `region` (`auto`), `pathStyle`, `secretRef {name, accessKeyIdKey: access-key-id, secretAccessKeyKey: secret-access-key}`, `cidrs`. |
| `storage.provisioned` | | `size` (50Gi), `storageClassName`: single-node Garage. |
| `masterKeyRef` | generated | `{name, key}` of an existing 32-byte key; otherwise `<name>-master-key` is generated once. |
| `replicas` | 2 | API replicas without autoscaling (one for single-writer releases). |
| `autoscaling` | none | `minReplicas`, `maxReplicas`, `targetCPUUtilizationPercentage` (70): an HPA. |
| `resources` | 100m/128Mi, 1Gi limit | API pod resources. |
| `ingress` | required | `className` (Ingress) **or** `gateway {name, namespace, sectionName}` (HTTPRoute); `issuerRef {name, kind: ClusterIssuer\|Issuer}` (cert-manager); `tlsSecretName` (`<name>-tls`); `annotations`. |
| `backup` | none | Provisioned PostgreSQL only (CEL): `schedule` (six-field cron, `0 0 3 * * *`), `retention` (`30d`), `destination {destinationPath: s3://…, endpointURL, secretRef}`. |
| `quotas` | service defaults | `deploymentBytes`, `projectBytes`, `memberBytes`. |
| `auditRetentionDays` | 400 | 30–3650. |
| `extraOrigins` | none | Further CORS origins, for example the public app. |
| `networkPolicy` | | `ingressNamespaceSelector` (the ingress controller's namespace; any when empty), `oidcCidrs`. |
| `images` | `<registry>/…` | `api`, `web`, `worker`, `garage`, `pullPolicy`, `pullSecrets`. |
| `deletionPolicy` | `Retain` | `Retain` or `Delete` ([Uninstall](#uninstall)). |

Further CEL rules: exactly one of `postgres.external`/`provisioned` and of
`storage.s3`/`provisioned`, and neither may switch after creation (that would start from an
empty database or bucket); `ingress` uses `className` or `gateway`, not both; provider names are
unique; `maxReplicas ≥ minReplicas`; the resource name is at most 40 characters.

## Status and troubleshooting

`kubectl -n <ns> get scr` shows domain, running version and readiness;
`kubectl -n <ns> describe scr <name>` shows conditions and events. Status fields: `version`
(running), `migratedVersion`, `url`, `masterKeySecret`, `storageBootstrapped`,
`compileWorkers {desiredReplicas, queueLength}`.

| Condition | Reasons | What to do |
| --- | --- | --- |
| `Ready` | `Ready`, `NotReady`, `InvalidSpec`, … | True when the API and web Deployments have available pods and the database and storage are ready. |
| `Progressing` | `WaitingForDependencies`, `Migrating`, `StoppingSingleWriter`, `RollingOut`, `Complete` | Normal during install and upgrades. |
| `Degraded` | `InvalidSpec`, `MigrationFailed`, `UnknownVersion` | `InvalidSpec` quotes the service's refusal (field named, never a value). `MigrationFailed`: read the Job's logs, fix, `kubectl delete job <name>-migrate-<version>` to retry. |
| `UpgradeBlocked` | `Downgrade`, `UnknownVersion`, `UnsupportedUpgradePath`, `MigrationFailed`, `None` | The running release keeps serving. Set `version` back, upgrade the operator, or go through the named intermediate release. |
| `DatabaseReady` | `SecretMissing`, `CloudNativePGMissing`, `Provisioning`, `Ready` | `CloudNativePGMissing`: install CloudNativePG or use `postgres.external`. |
| `StorageReady` | `SecretMissing`, `Provisioning`, `Bootstrapping`, `Ready` | `Bootstrapping` repeats until Garage's admin API answers; its message has the error. |

Events: `MasterKeyGenerated`, `MigrationStarted`, `Migrated`, `Installed`, `Upgraded`,
`UpgradeBlocked`, `MigrationFailed`, `StorageBootstrapped`, `AutoscalingIgnored`, `Retained`,
`DataDeleted`. The operator logs JSON lines (`RUST_LOG`), serves Prometheus metrics on
`:8080/metrics` (`scribyra_operator_reconciliations_total{result}`,
`scribyra_operator_reconcile_duration_seconds`, `scribyra_operator_leader`,
`scribyra_operator_compile_queue_length{namespace,name}`), `/healthz` and `/readyz` (ready only
on the leader).

## Upgrades

Changing `spec.version`:

1. The operator checks the path against the releases it knows (`crates/operator/src/versions.rs`,
   each with the releases it may be upgraded from). A downgrade, an unknown release or a skipped
   required release sets `UpgradeBlocked` and changes nothing. Upgrading the operator first is how
   it learns new releases. (The annotation `scribyra.com/allow-unknown-version: "true"` admits
   development builds; never in production.)
2. It runs the migration Job `<name>-migrate-<version>` with the new image while the old release
   keeps serving, and waits for it to complete. The schema is **never rolled back
   automatically**: migrations are append-only and a rollback is a restore of a pre-upgrade
   backup with the old release.
3. Only then are the API, web and worker Deployments rolled to the new image (`maxUnavailable:
   0`). A failed Job leaves the old release serving and reports `MigrationFailed`.

**Single-writer releases.** Until slice 19 the API holds a PostgreSQL advisory lock as the
database's only writer (`docs/service.md`), so a second API process, or the migration Job, cannot
start while one runs. For releases marked `single_writer` (all current ones) the operator runs one
API replica with a `Recreate` strategy (autoscaling is ignored, with an event), and on upgrade
scales the API and workers to zero, waits until their pods are gone, runs the migration, then
starts the new release: a short outage per upgrade. If the migration fails, the old release is
scaled back up.

The operator itself upgrades like any Deployment (apply the new `operator.yaml`); it holds no
state besides the resources' status.

## Backup and restore

What must be backed up, in this order (design [Appendix B](org-sync-design.md#appendix-b-operator-backup-and-restore)):
the **database** first, then the **object storage**, and separately the **master key**.

- **Provisioned PostgreSQL**: `spec.backup` makes the CloudNativePG `Cluster` archive WAL and base
  backups to S3 (Barman Cloud) and creates a `ScheduledBackup`. Point-in-time recovery follows
  from WAL archiving. (CloudNativePG 1.26+ prefers its Barman Cloud plugin over the in-tree
  `barmanObjectStore` the operator configures; moving to the plugin is open work.)
- **External PostgreSQL**: your provider's backups, or `pg_dump` as in service.md.
- **Object storage**: external S3: bucket versioning or replication. Provisioned Garage: copy the
  bucket with any S3 tool using the `<name>-garage-s3` credentials (for example `rclone sync`
  through `kubectl port-forward svc/<name>-garage 3943` with the CA from `<name>-garage-tls`),
  or snapshot its volume. The operator does not schedule this yet.
- **Master key** (`<name>-master-key` or your `masterKeyRef`): export once and keep it apart from
  the database backups. Without it server-readable projects cannot be decrypted.

**Restore** (not automated yet; a `restoreFrom` field is planned): create the namespace, the
master key Secret under the same name and key, the storage (restore the bucket, or the Garage
volume and its `-garage-*` Secrets), and a CloudNativePG `Cluster` named `<name>-db`
bootstrapped with `recovery` from the backup, *before* applying the `Scribyra`; the operator then
adopts them by name. Run `scribyra-sync verify` as a Job before switching clients. This path is
untested until a real cluster exists.

## Uninstall

Deleting a `Scribyra` runs the operator's finalizer `scribyra.com/cleanup`:

- `deletionPolicy: Retain` (default): owned objects (Deployments, Services, Jobs, policies, the
  configuration Secret, Garage's StatefulSet) are removed through owner references; the
  CloudNativePG `Cluster` and its volumes, the Garage volume, `<name>-garage-s3` and the generated
  master key stay (an event lists them). Recreating the resource with the same name adopts them.
- `deletionPolicy: Delete`: additionally deletes the CloudNativePG `Cluster` (and so its
  volumes), the Garage volume claims, `<name>-garage-s3` and the generated master key. A
  `masterKeyRef` Secret is yours and is never deleted.

Then remove the operator: `kubectl delete -f deploy/operator/operator.yaml` (or `helm
uninstall`). **Deleting the CRD deletes every `Scribyra` in the cluster**: delete the resources
first, deliberately.

## Security model

- **Operator RBAC** (`manifests::cluster_rules`, identical in the manifest and the chart): only
  the kinds it manages, with `get list watch create patch delete` (no `update` except on its own
  resource, no `escalate`, `bind`, `impersonate` or wildcards); `pods` list only (to wait for a
  single writer to stop); `persistentvolumeclaims` list and delete (for `Delete`); events; the
  lease only in its namespace and only by name for `get`/`patch`. Its Secret permissions are
  cluster-wide because the generated Secrets live in tenants' namespaces; it reads referenced
  Secrets only to check that their keys exist and never copies their values into anything it
  writes. With `watchNamespace` it reconciles one namespace, but Kubernetes RBAC cannot narrow
  the ClusterRole by namespace; bind a namespaced Role instead if that matters. The integration
  tests act as this service account, so missing permissions fail them.
- **Pods** meet the Pod Security `restricted` standard: non-root (UID 10001), no privilege
  escalation, all capabilities dropped, `RuntimeDefault` seccomp, read-only root file system,
  no service account token mounted. The operator's namespace is labelled
  `pod-security.kubernetes.io/enforce: restricted`; label tenant namespaces the same way.
- **Secrets** reach pods only as read-only files (mode 0440) or, for the S3 access key ID, an
  environment variable from the Secret. The generated configuration holds paths, never values.
- **Network policies**: default deny for every pod of the instance; the web app accepts its port
  from the ingress controller's namespace and has no egress; the API accepts 8787 from there and
  metrics from the operator's namespace, and reaches only DNS, PostgreSQL, storage and HTTPS for
  the OIDC issuers; the migration Job reaches DNS, PostgreSQL and storage; compile workers reach
  DNS, PostgreSQL and storage only, never the internet (they take jobs from the PostgreSQL queue,
  so "no egress at all" is not possible; nothing else is open); Garage accepts S3 from those
  components and its admin port from the operator only; CloudNativePG pods accept 5432 from them.
  NetworkPolicy cannot name hosts: external PostgreSQL, S3 and OIDC are reached by `cidrs`
  (`0.0.0.0/0` on the one port when empty); use a CNI with FQDN policies to narrow them further.
  Policies need a CNI that enforces them (k3s's flannel with its network policy controller does).
- **In-cluster storage TLS**: Garage listens on loopback; a TLS proxy (the operator image) in its
  pod serves the S3 and admin APIs with a certificate from a per-deployment CA the operator
  generates. The service trusts only that CA for its endpoint (`s3_ca_file`), the operator only
  that CA for the admin API.
- **Compile workers**: `hostUsers: false`, memory-backed size-limited scratch, optional gVisor.
  bubblewrap inside the worker needs user namespaces, which `RuntimeDefault` seccomp may refuse on
  some runtimes; a `Localhost` profile may be needed (untested; slice 15).
- **Forwarded addresses**: the service trusts no forwarded headers by default, so its per-source
  rate limits see the ingress controller's address. `trusted_proxies` takes addresses, not
  ranges, which does not fit pod IPs; it is left empty until the service accepts a range.

## Multi-tenant hosting

One `Scribyra` per customer namespace. Per tenant: a namespace labelled for Pod Security
`restricted`, a `ResourceQuota` and `LimitRange`, its own CloudNativePG cluster (or a database on
a shared one through `postgres.external`), its own bucket (`storage.s3` with per-tenant
credentials), `compile.runtimeClassName: gvisor` so tenants' compile jobs never share a host
kernel, and `networkPolicy.ingressNamespaceSelector` naming the shared ingress or gateway
namespace. Tenants never share pods; every object carries `scribyra.com/instance`. Billing and
sign-up stay outside the product and create or update `Scribyra` resources (design slice 22).

## Contract with the service

The operator writes `service.json` with only the fields it sets, and serialises the service's own
`config::Deployment` type, so a renamed service field fails the operator's build; the test
`generated_configuration_passes_the_services_validation` parses it strictly and runs
`Config::validate`. Paths, ports, commands and metric names both sides use are in
`crates/sync/src/deploy.rs` (`scribyra_sync::deploy`), which was added for the operator. Added to
the service with it: `scribyra-sync migrate` and the `s3_ca_file` field (service.md).

Not yet in the service, used by the operator already (it tolerates their absence): the metrics
port 9090 with `scribyra_compile_queue_length`, `scribyra-sync compile-worker` and the worker
image with TeX Live at `/opt/texlive`, multi-writer releases (slice 19).

The design text in section 10 sketches the resource with group `scribyra.org`, providers at the
top level and `encryption: server|e2ee`; the operator follows the 18 November brief instead:
`scribyra.com`, `oidc.providers`, `encryption: serverReadable|endToEnd`, `policy.*`.

## Testing, and what is not tested yet

```sh
nix develop .#operator -c cargo test -p scribyra-operator
```

- **Unit and snapshot tests** (`tests/manifests.rs`): every generated manifest for the three
  samples is pinned in `tests/snapshots/` (`UPDATE_SNAPSHOTS=1` rewrites them; review the diff);
  `operator.yaml`, the chart's CRD and RBAC rules match the generator; the generated
  configuration passes the service's validation; every pod meets `restricted`; secrets are files;
  policies, owner references, single-writer handling, HPA, workers and routing are checked.
- **Integration tests** (`tests/envtest.rs`): etcd, kube-apiserver (RBAC on) and
  kube-controller-manager (garbage collector, Deployment, ReplicaSet, StatefulSet controllers;
  no Job controller, kubelet or scheduler) as plain processes from nixpkgs. The controller runs as
  the operator's service account. Covered: CRD schema and CEL rules (including immutable
  fields) enforced by the API server; install waiting for secrets; the migration Job before the
  first API Deployment; upgrade ordering (no rollout until the Job completes); downgrade,
  unknown and skipped releases blocked; single-writer upgrades stopping the old pods before the
  Job; a failed migration scaling the old release back; finalizer behaviour for `Retain` and
  `Delete` with real garbage collection; pruning when components are turned off; invalid specs
  reported without deploying; CloudNativePG missing, then the `Cluster`, `ScheduledBackup` and
  readiness with its CRDs; leader election and its RBAC.
- **Garage** (`tests/garage.rs`): a real Garage 1.x from the generated `garage.toml`, behind the
  operator's TLS proxy and CA; the admin-API bootstrap (twice, idempotent; wrong token refused);
  the service's S3 client storing and reading through it with only that CA, and refusing without
  it.
- **CI**: `.github/workflows/operator.yml` runs all of the above, the Helm lint, actionlint and
  the image build on pull requests that touch the operator or the service.
  `.github/workflows/operator-e2e.yml` (manual, optional until stable) installs CloudNativePG and
  the operator on kind and waits for a quickstart-like deployment to become Ready.

**Untested until a real cluster exists**: pods actually starting (images, probes, read-only root
with the service, mounted files' ownership), scheduling and volumes, NetworkPolicy enforcement,
CloudNativePG provisioning and backups, Garage in a pod and its sidecar, Ingress, HTTPRoute and
cert-manager TLS, HPA and KEDA scaling, gVisor and user namespaces for workers, the operator's
own Deployment, probes and lease across pods, restore, and multi-arch images (only the build
host's architecture was built here).
